BUG-01 · 密码错误也能登录成功

严重 POST /api/login

怎么复现：

POST http://127.0.0.1:8124/api/login
Content-Type: application/json

{ "username": "admin", "password": "随便乱填一个" }

预期：200，code=1001，提示用户名或密码错误。
实际：200，code=0，msg=登录成功，还发了一个 token 出来。

为什么是问题：这意味着任何人随便输个密码都能登录任何账号，登录功能等于没有。

怎么发现的（关键思路）：把"密码正确"和"密码错误"两条用例放在一起对比。
再补一条"用户名不存在"——你会发现用户名错了会正常报 1001，偏偏密码错了不报。这个对比一做出来，问题就藏不住了。

BUG-02 · 登录返回体里带明文密码

严重 POST /api/login

怎么复现：正常登录一次，看返回的 JSON：

{
  "code": 0,
  "msg": "登录成功",
  "data": {
    "token": "tk_admin_...",
    "userId": 1,
    "username": "admin",
    "password": "123456",     // 这个字段不该出现
    "role": "管理员"
  }
}

预期：接口文档写明"返回的用户信息中不允许包含密码"。
实际：密码明文出现在返回数据里。

为什么是问题：任何人打开 F12 或抓个包就能看到密码。如果用的是相同的密码注册了别的网站，直接连坐。

怎么发现的：拿到一个接口的返回，别只看"成没成功"，把每个字段都念一遍：这个字段前端需要吗？不用的字段为什么给我？
这是接口测试里一条很值钱的习惯 —— 敏感信息检查。

BUG-03 · page 参数失效，翻页翻不动

中等 GET /api/cows

怎么复现：

GET http://127.0.0.1:8124/api/cows?page=1&size=5    → 返回 A0001 ~ A0005
GET http://127.0.0.1:8124/api/cows?page=2&size=5    → 还是 A0001 ~ A0005  // 应该是 A0006 ~ A0010

预期：page=2 应该返回第 6~10 条。
实际：返回的还是第一页的内容，page 原样回显成 2，但数据没变。

为什么是问题：用户永远看不到第 2 页以后的数据。

这题的陷阱：很多人测翻页只看"有没有数据返回"，看到有数据就过了。
正确做法：把第一页和第二页的内容对比一下（比如看 id 或耳标号），确认两页不是同一批数据。
更省事的办法：看 page=2 返回的第一条 id 是不是接着第一页往下排的。

BUG-04 · 筛选之后 total 不对

中等 GET /api/cows

怎么复现：

GET http://127.0.0.1:8124/api/cows?breed=荷斯坦

{
  "data": {
    "total": 10,        // 应该是 3
    "list": [ 3 条荷斯坦 ]
  }
}

预期：total 是"符合筛选条件的总条数"，荷斯坦只有 3 头，total 应为 3。
实际：total 永远是全部牛只数 10。

为什么是问题：前端拿 total 算"一共几页"，就会显示一堆点进去是空的页。

通用套路记一下：只要接口里有筛选条件，就一定要检查 total（或 count 之类的字段）有没有跟着筛选走。这类缺陷特别常见，而且特别容易被漏掉。

BUG-05 · 缺必填参数返回 500，还把内部报错吐出来

中等 POST /api/cows

怎么复现：带 token，Body 里故意不写 ear_tag：

POST http://127.0.0.1:8124/api/cows
Authorization: tk_admin_...

{ "breed": "安格斯", "gender": "公", "in_date": "2026-09-20", "weight": 520.5 }

// 返回 500
// { "code": 5000, "msg": "服务器内部错误",
//   "data": { "error": "Cannot read properties of undefined (reading 'trim')" } }

预期：400，code=1002，提示"ear_tag 不能为空"。
实际：500，并且把程序内部的报错原文返回出来了。

为什么是问题：两个问题叠在一起：
1. 参数校验缺失 —— 用户少填一个字段，程序就崩；
2. 信息泄露 —— 把内部错误信息给到了外部，懂行的人能从中看出你用什么技术、代码怎么写的。

要区分清楚：400 是"你参数写错了"，500 是"我程序崩了"。
用户填错东西天经地义，程序应该好好提示；一崩就返回 500，是程序的问题。
所以测试时看到 500，不要当成"我请求发错了"就跳过去 —— 那大概率是个缺陷。

BUG-06 · 耳标号重复也能新增成功

中等 POST /api/cows

怎么复现：用已经存在的耳标号 A0001 再新增一次：

POST http://127.0.0.1:8124/api/cows
{ "ear_tag": "A0001", "breed": "安格斯", "gender": "公", "in_date": "2026-09-20", "weight": 520.5 }

// 返回 201 新增成功，库里出现了两个 A0001

预期：接口文档写了"耳标号必须唯一"，应该返回 400 + code 1002，提示耳标号已存在。
实际：新增成功，数据库里出现两条一样的耳标号。

为什么是问题：以后按耳标号查这头牛会查出两条，饲喂记录也对不上号，整个系统的数据都会乱。

通用套路：凡是文档写了"唯一"的字段（手机号、身份证、编号、邮箱），都要用"库里已经有的值"再提交一次来验证。这条几乎每个项目都会有类似的用例。

BUG-07 · 删除接口没校验 token（未登录也能删数据）

严重 DELETE /api/cows/{id}

怎么复现：发起删除请求，但请求头里不带 Authorization：

DELETE http://127.0.0.1:8124/api/cows/12

// 返回 200，删除成功，数据真的没了

预期：文档写明"删除牛只需要登录"，应该返回 401 + code 2001。
实际：200，删除成功。

为什么是问题：任何人都能删掉系统里的数据，属于越权，是安全类里比较严重的一种。

这个缺陷有个很有说服力的旁证：同一个系统的「新增牛只」接口是会校验 token 的（不带 token 返回 401）。
新增校验了、删除没校验 —— 说明这是漏写，不是设计如此。
在缺陷报告里写出这个对比，开发一眼就知道要去改哪里，这就是"高质量的缺陷报告"。

你找到几个？

  • 找到 3 个以下 —— 正常，第一次做接口测试都这样。重点看你是不是只测了"正常能过"的情况。
  • 找到 3~5 个 —— 入门了，说明你已经会往异常路径上想。
  • 找到 6~7 个 —— 很好，这套方法论可以直接拿去测真实项目了。
这次练习真正要带走的三句话：
1. 接口测试的重点在异常，不在"能不能跑通"；
2. 增删改之后一定再查一次；
3. 带筛选条件时一定看 total。
